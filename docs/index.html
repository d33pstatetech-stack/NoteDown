NoteDown

A local-first Markdown notes app. Your notes live in a SQLite database on your own machine and the app works completely offline. Signing in to an account is optional and only adds sync between devices.

Windows & Linux Offline-first Plain Markdown export No account required
Live and verified

This page was checked against the running application. The installer path, the toolchain versions and the file locations below all reflect a real build on Windows 11.

Quick start

Windows

1

Install the prerequisites.

ToolVersionInstall
Node.js 20.19+ winget install OpenJS.NodeJS.LTS
Rust stable winget install Rustlang.Rustup
pnpm 9.x npm install -g pnpm
Visual Studio Build Tools 2022 or newer, Desktop development with C++ same page, choose the C++ workload
2

Build and run.

# PowerShell
git clone https://github.com/d33pstatetech-stack/NoteDown.git
cd NoteDown
corepack enable
pnpm install
pnpm dev:desktop

The app window opens and you can write notes immediately. No account needed.

Building in a path with spaces?

Windows builds fail with cc1.exe: fatal error and windres: preprocessing failed if the repository sits somewhere like C:\Users\me\My Projects\NoteDown. Either clone to a path without spaces, or set the target directory — see Troubleshooting.

Making an installer

Use this when you want a standalone app instead of running from source.

# run from source, with hot reload
pnpm dev:desktop

# produce an installer
pnpm --filter @localnotes/desktop run build

The installer lands in the Rust target directory, which is under the desktop app's src-tauri folder by default. Both paths are relative to the repository root:

OSPath
Windows apps\desktop\src-tauri\target\release\bundle\nsis\NoteDown_<version>_x64-setup.exe
Linux apps/desktop/src-tauri/target/release/bundle/nsis/NoteDown_<version>_x64-setup.exe

If you set CARGO_TARGET_DIR, the output moves there instead — for example C:\nd-target\release\bundle\nsis\.

Windows notes

The installer is an NSIS package — run it and follow the prompts. Microsoft Edge WebView2 must be installed; it ships with Windows 11 and current Windows 10. If the app opens to a blank window, install it from Microsoft.

Windows may warn about an unrecognised publisher. This is expected: the app is not code-signed.

Linux notes

webkit2gtk provides the web view. It is the dependency most likely to be missing if the build fails.

To ship .deb or .AppImage instead, add those targets to bundle.targets in apps/desktop/src-tauri/tauri.conf.json — currently ["nsis"]. Launchers appear in your application menu after install.

Optional: connecting an account

Sign in from the app to sync notes across devices. Skipping this is fine — the app is fully functional offline and nothing is stored on a server.

The built app points at the hosted sync service:

https://notedown-api.d33pstatetech.workers.dev

To build against a different backend, set the URL before building:

# Linux / macOS
VITE_API_URL=https://your-worker.example.workers.dev \
  pnpm --filter @localnotes/desktop run build

# Windows PowerShell
$env:VITE_API_URL="https://your-worker.example.workers.dev"
pnpm --filter @localnotes/desktop run build

If VITE_API_URL is not set, the app builds and runs in local-only mode with sync disabled. That is a supported configuration, not an error.

Content Security Policy

When you point the app at a different backend, add that origin to the connect-src entry in apps/desktop/src-tauri/tauri.conf.json. The Content Security Policy blocks any origin that is not listed, so a mismatch shows up as the app silently failing to sync.

Troubleshooting

pnpm: command not found

Install it with npm install -g pnpm@9, or run corepack enable in the repository first.

Windows build fails in windres or cc1.exe

Both MinGW and MSVC struggle with spaces in paths. Move the repository to a path without spaces, or point the build somewhere clean: 

# PowerShell
$env:CARGO_TARGET_DIR = "C:\nd-target"
pnpm --filter @localnotes/desktop run build

pkg-config could not find webkit2gtk-4.1

Install the webkit2gtk development package for your distribution. Tauri 2 needs the 4.1 series, not the older webkit2gtk2gtk-4.0.

error while loading shared libraries

The build succeeded but the app will not start — you built against a newer webkit than the system provides at runtime. Install webkit2gtk-4.1 as a normal (non-dev) package as well.

Blank white window

Almost always a missing WebView2 runtime on Windows. See the WebView2 note above.

The first build is slow

Expected. Rust compiles the standard library and the Tauri stack from source on a cold build, which takes several minutes. Later builds are much faster.

Sign-in fails but the app otherwise works

Expected when the network is unavailable. Local notes are unaffected and stay on the machine; sync resumes on its own once the connection is back.

Where your notes are stored

Notes are a plain SQLite database in your user data directory. Copy that directory to back everything up.

OSLocation
Windows %APPDATA%\com.notedown.app\
Linux ~/.local/share/com.notedown.app/
(or $XDG_DATA_HOME/com.notedown.app/)
macOS ~/Library/Application Support/com.notedown.app/

Inside that directory:

  • notes.sqlite3 — notebooks, folders, notes, attachments, the sync queue, tombstones and checkpoint.
  • notes.sqlite3-wal / notes.sqlite3-shm — write-ahead log. Copy them together with the database.
  • attachments/ — image bytes, named by stable attachment UUID.

SQLite runs with journal_mode = WAL, foreign_keys = ON, synchronous = NORMAL and busy_timeout = 5000. Migrations are explicit, versioned and applied on startup; the applied version is stored in the schema_migrations table.

Backing up

Simplest: quit the app, then copy the whole com.notedown.app directory. Restoring is copying it back.

Live backup without quitting:

sqlite3 notes.sqlite3 "VACUUM INTO 'backup.sqlite3'"
Most portable

The in-app Export button produces a ZIP of plain Markdown files. That format needs no SQLite at all, and the desktop app can read it back.

In the browser

Everything lives in IndexedDB under the origin you loaded the app from (the localnotes database, with the nodes, attachments, queue and meta stores).

IndexedDB is not a guaranteed filesystem

Storage may be evicted under pressure, is cleared by “clear site data” and private browsing, and is not restored by uninstalling the browser.

  • The app requests persistent storage (navigator.storage.persist()), reports the result in Settings → Storage, and shows a persistent warning when the origin is best-effort rather than persistent.
  • Per-origin allowance, eviction policy and “persistent” behaviour differ by browser and change over time, so the in-app status panel reads the real values from navigator.storage.estimate() instead of hard-coding them.
  • Export regularly. Export → ZIP is the only browser backup that survives clearing site data.

Security

Trust boundaries

BoundaryAssumptionControl
Browser ↔ Worker Network is hostile HTTPS only. Restrictive CORS — Access-Control-Allow-Origin is exactly the app origin, no wildcard — and CSRF-protected state-changing routes.
Desktop ↔ Worker Same, plus no cookie jar Better Auth bearer plugin. The session token is read from set-auth-token, kept in OS-protected storage by the Rust core, and sent as Authorization: Bearer.
Worker ↔ D1 / R2 Trusted Bindings only. No Cloudflare API token in any client and no credentials in the repository.
Client → client Never trusted Ownership is enforced in SQL (WHERE user_id = ?) from the verified session. Ids in request bodies are ignored.
Why the browser uses a bearer token too

The hosted web app and the Worker are different sites. A SameSite=Lax session cookie would be withheld by the browser on cross-site requests, so sign-in would appear to succeed while every later request stayed anonymous. Both clients therefore send an explicit bearer token: the desktop through the Rust core, the browser from localStorage.

Authentication

  • Better Auth with the D1 binding (database: env.DB). No hand-rolled password hashing, session tokens or crypto.
  • Passwords are hashed by the library (scrypt/argon2 per its own defaults), never logged and never stored by NoteDown.
  • Email verification and password reset need an email transport, which is an external service. Until one is configured the app runs without email verification for the single-user case, and the UI says so.
  • Sessions are server-side rows in D1; signing out deletes the row. On startup the app calls GET /api/me — a 401 only downgrades it to offline mode, never an error state.

Authorization

  • Every /api/* route resolves the user from the session before touching data.
  • Cross-user access is prevented by scoping every read and write by user_id, and by returning 404 rather than 403 for another user's id, so ids are not enumerable.
  • Tested: cross-user notes, attachments and tombstones return 404; an unauthenticated request returns 401; a forged user_id in the body is ignored.
  • Attachment downloads are authorized the same way. R2 buckets are private: no public bucket URL and no r2.dev public access.

Attaching local data to an account

An existing local database is never silently bound to whichever account signs in. The app records a localOwnerId once linked; if a different account signs in it refuses to sync and offers Link account, Export or Import. Unlinking is explicit and requires typing the account email to confirm.

Input validation

  • Attachment MIME type is sniffed from the bytes, not taken from the client's Content-Type, and the extension is derived from the sniffed type against an image allow-list.
  • Limits: 5 MiB per attachment and 2 MiB of Markdown per note; sha256 is verified on commit.
  • Filenames from a client are used for display only, never to build a filesystem path.
  • Import rejects any archive entry that is absolute, has a drive letter, contains .., backslashes, NUL or a symlink, or exceeds limits.

Secrets

  • No real credentials in the repository; .env.example holds placeholders only.
  • Cloudflare secrets are set with wrangler secret put <NAME>. Account and database ids live in wrangler.jsonc — they are identifiers, not secrets — but .env is git-ignored regardless.
  • Better Auth's secret must be at least 32 random bytes. Rotating it invalidates existing sessions, which is the documented recovery path if it ever leaks.

What is not protected yet

Know these limits
  • No end-to-end encryption. The server can read note content — required for server-side export and validation. Encryption at rest is R2's and D1's, not NoteDown's.
  • No per-note sharing, no public links, no audit log.
  • Local data at rest is not encrypted. Anyone with filesystem access to your machine or browser profile can read your notes. Full-disk encryption is the mitigation.
